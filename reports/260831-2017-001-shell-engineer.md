## What changed and why

Added first-class root-project support for the reserved project id `jarvis`, centralized in one
resolver rather than scattered `if project == jarvis` branches, per the task brief.

- `scripts/herdr-runtime-lib.sh`: added `JARVIS_ROOT_PROJECT_ID` and `project_root_path()` — the
  single resolver from a project id to its physical checkout path (`jarvis` → `$HARNESS_ROOT`,
  everything else → `$HARNESS_ROOT/projects/<name>`). Widened `plan_card_matches()` to also scan the
  root `plan/` (gated on its existence) alongside every `projects/*/plan/`, so task lookup covers
  both without changing the nested-scan behavior at all. `card_project()` now recognizes a card under
  `$HARNESS_ROOT/plan/` as belonging to `jarvis`, and refuses (dies, message contains "reserved") a
  card physically found under a would-be `projects/jarvis` — that name collides with the reserved id,
  so it's rejected rather than silently misread. `role_path()` now routes through
  `project_root_path()` instead of hardcoding `projects/$project/agents/`; for `jarvis` this
  collapses to `$HARNESS_ROOT/agents/` on both the primary and fallback legs (root role resolution
  uses root `agents/`, unchanged fallback for nested projects).
- `scripts/agent-spawn.sh`: the one caller that previously computed `PROJECT_ROOT` by hand now
  consumes `project_root_path()` — the only production-code change needed to make root task worktrees
  and roles resolve correctly. Since `git worktree add` never mutates the checkout it's run against
  (it only registers a new linked worktree), spawning a root-owned task leaves the main checkout's
  branch, HEAD and tracked status untouched — verified in
  `tests/root-project-lifecycle.test.sh`.
- `scripts/onboard-project.sh`: now sources `herdr-runtime-lib.sh` for the shared resolver instead of
  reimplementing project-path logic. For the reserved `jarvis` id it accepts an already-existing root
  `plan/` (this harness's own — dogfooding) instead of refusing like nested onboarding does, and only
  creates whichever of `plan/TEMPLATE.md` / `plan/INDEX.md` is still missing; re-running it against an
  already-onboarded root is idempotent (prints "already up to date", exits 0) rather than failing.
  Nested-project behavior (unconditional creation, refuse if `plan/` exists) is byte-for-byte
  unchanged — verified by the pre-existing `tests/onboard-project.test.sh`, updated only to copy the
  now-required `herdr-runtime-lib.sh` fixture dependency.
- `RULES.md`, `templates/plan-task-card.md`, `plan/TEMPLATE.md`: updated the "there is no shared
  plan/ at the harness root" claims to state the one reserved exception and point at
  `project_root_path`, limited to that contract — no other rule text touched.
- New tests: `tests/root-project.test.sh` (resolver unit tests: `project_root_path`, ordinary vs.
  root `task_card`/`card_project` resolution, legacy `Tnn` and timestamp ids at the root, ambiguous
  duplicate-id refusal between root and nested plans, `role_path` reading root `agents/`, and the
  `projects/jarvis` reserved-name-collision refusal) and `tests/root-project-lifecycle.test.sh`
  (`onboard-project.sh jarvis` accept/idempotent behavior end-to-end, then `agent-spawn.sh` against a
  root-owned card: worktree + branch created against the harness root repo, root-agents role used,
  recorded `project_root` resolves to the harness root, and the main checkout's branch/HEAD/tracked
  status are provably unchanged after spawn).

## What I rejected, and why

- Did not add a new `scripts/project-lib.sh` file. The task said "centralize... in one resolver";
  `scripts/herdr-runtime-lib.sh` already owns `task_card`/`card_project`/`role_path`, so adding the
  resolver there keeps every project-path-aware function in the one file that already had them,
  rather than splitting related logic across two files for no functional gain.
- Did not touch `scripts/task-teardown.sh`'s own `PROJECT_ROOT` fallback (`meta_get ... project_root`
  else `$HARNESS_ROOT/projects/$PROJECT`). `agent-spawn.sh` now always records the correct resolved
  `project_root` in task metadata, so that fallback is legacy-metadata-only and out of the brief's
  named scope (`agent-review.sh`, `agent-wait.sh`, QA routing, lead relaunch were explicitly
  out-of-scope; teardown wasn't named in-scope either, and the brief's required proof — role/worktree
  resolution at spawn time — doesn't touch it).
- Did not touch `docs/herdr-runtime.md`, which also states "never in a projects/<project>/plan/" —
  that's documentation, not "template/rule text", and outside this card's `Owns:` list; touching it
  would have swept in a second file class the brief didn't name.
