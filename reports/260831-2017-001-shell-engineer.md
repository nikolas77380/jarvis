## What changed and why

Added first-class root-project support for the reserved project id `jarvis`, centralized in one
resolver rather than scattered `if project == jarvis` branches, per the task brief.

- `scripts/herdr-runtime-lib.sh`: added `JARVIS_ROOT_PROJECT_ID` and `project_root_path()` — the
  single resolver from a project id to its physical checkout path (`jarvis` → `$HARNESS_ROOT`,
  everything else → `$HARNESS_ROOT/projects/<name>`). Widened `plan_card_matches()` to also scan the
  root `plan/` (gated on its existence) alongside every `projects/*/plan/`, so task lookup covers
  both without changing the nested-scan behavior at all. `card_project()` now recognizes a card under
  `$HARNESS_ROOT/plan/` as belonging to `jarvis`, and refuses (dies, message contains "reserved") a
  card physically found under a would-be `projects/jarvis` — that name collides with the reserved id,
  so it's rejected rather than silently misread. `role_path()` now routes through
  `project_root_path()` instead of hardcoding `projects/$project/agents/`; for `jarvis` this
  collapses to `$HARNESS_ROOT/agents/` on both the primary and fallback legs (root role resolution
  uses root `agents/`, unchanged fallback for nested projects).
- `scripts/agent-spawn.sh`: the one caller that previously computed `PROJECT_ROOT` by hand now
  consumes `project_root_path()` — the only production-code change needed to make root task worktrees
  and roles resolve correctly. Since `git worktree add` never mutates the checkout it's run against
  (it only registers a new linked worktree), spawning a root-owned task leaves the main checkout's
  branch, HEAD and tracked status untouched — verified in
  `tests/root-project-lifecycle.test.sh`.
- `scripts/onboard-project.sh`: now sources `herdr-runtime-lib.sh` for the shared resolver instead of
  reimplementing project-path logic. For the reserved `jarvis` id it accepts an already-existing root
  `plan/` (this harness's own — dogfooding) instead of refusing like nested onboarding does, and only
  creates whichever of `plan/TEMPLATE.md` / `plan/INDEX.md` is still missing; re-running it against an
  already-onboarded root is idempotent (prints "already up to date", exits 0) rather than failing.
  Nested-project behavior (unconditional creation, refuse if `plan/` exists) is byte-for-byte
  unchanged — verified by the pre-existing `tests/onboard-project.test.sh`, updated only to copy the
  now-required `herdr-runtime-lib.sh` fixture dependency.
- `RULES.md`, `templates/plan-task-card.md`, `plan/TEMPLATE.md`: updated the "there is no shared
  plan/ at the harness root" claims to state the one reserved exception and point at
  `project_root_path`, limited to that contract — no other rule text touched.
- New tests: `tests/root-project.test.sh` (resolver unit tests: `project_root_path`, ordinary vs.
  root `task_card`/`card_project` resolution, legacy `Tnn` and timestamp ids at the root, ambiguous
  duplicate-id refusal between root and nested plans, `role_path` reading root `agents/`, and the
  `projects/jarvis` reserved-name-collision refusal) and `tests/root-project-lifecycle.test.sh`
  (`onboard-project.sh jarvis` accept/idempotent behavior end-to-end, then `agent-spawn.sh` against a
  root-owned card: worktree + branch created against the harness root repo, root-agents role used,
  recorded `project_root` resolves to the harness root, and the main checkout's branch/HEAD/tracked
  status are provably unchanged after spawn).

## What I rejected, and why

- Did not add a new `scripts/project-lib.sh` file. The task said "centralize... in one resolver";
  `scripts/herdr-runtime-lib.sh` already owns `task_card`/`card_project`/`role_path`, so adding the
  resolver there keeps every project-path-aware function in the one file that already had them,
  rather than splitting related logic across two files for no functional gain.
- Did not touch `scripts/task-teardown.sh`'s own `PROJECT_ROOT` fallback (`meta_get ... project_root`
  else `$HARNESS_ROOT/projects/$PROJECT`). `agent-spawn.sh` now always records the correct resolved
  `project_root` in task metadata, so that fallback is legacy-metadata-only and out of the brief's
  named scope (`agent-review.sh`, `agent-wait.sh`, QA routing, lead relaunch were explicitly
  out-of-scope; teardown wasn't named in-scope either, and the brief's required proof — role/worktree
  resolution at spawn time — doesn't touch it).
- Did not touch `docs/herdr-runtime.md`, which also states "never in a projects/<project>/plan/" —
  that's documentation, not "template/rule text", and outside this card's `Owns:` list; touching it
  would have swept in a second file class the brief didn't name.

## What changed and why

Fixed all five round-1 findings (`reports/260831-2017-001-shell-reviewer.md`, verdict
REQUEST_CHANGES at tip `92dc2ee`) with TDD — a failing test against `92dc2ee` for each, confirmed
red, then the minimal fix, then green. Full findings and fixes recorded on the card under
`## Review round 1`; summary here:

- **Finding 1 (fleet-fork guard).** `scripts/herdr-runtime-lib.sh`: a `jarvis` task worktree is a
  linked worktree (`.git` is a file) carrying the harness's own `scripts/`, so the prior
  BASH_SOURCE-derived `HARNESS_ROOT` resolved to the worktree itself — a script run from inside it
  would create its own nested `.harness-worktrees`/`.harness-state`, forking a second fleet with no
  error. Added a guard right after the initial `HARNESS_ROOT` assignment: when `.git` is a file,
  re-resolve through `git -C "$HARNESS_ROOT" rev-parse --path-format=absolute --git-common-dir` and
  take its parent as the real `HARNESS_ROOT`. This is unconditional in the library (not scoped to
  individual "state-mutating" entry points) — every caller that sources the library gets the
  corrected root, which matches the existing "one resolver" approach rather than picking out call
  sites one by one. The cwd-relative scripts the review explicitly said not to touch
  (`plan-check.sh`, `checkpoint.sh`, `review-rounds.sh`) don't source this library and are
  unaffected. New test: `tests/root-project-worktree-guard.test.sh` (HARNESS_ROOT/STATE/WORKTREES
  and `task_card` resolve to the main checkout from inside a linked worktree; an ordinary checkout
  is unaffected).
- **Findings 2 and 3 (root plan discovery).** `scripts/session-start.sh` now resolves
  `--project jarvis` through `project_root_path`, and the no-project form enumerates the root
  `plan/INDEX.md` under a `-- jarvis --` section alongside every nested project.
  `scripts/fleet-snapshot.sh` now globs `plan/*.md` at the harness root in addition to
  `projects/*/plan/*.md`, so a root card with no runtime metadata yet (freshly minted or torn down)
  shows up in FLEET STATE. New test: `tests/root-project-discovery.test.sh`.
- **Finding 4 (task-teardown fallback).** `scripts/task-teardown.sh`'s legacy-metadata fallback
  (`project_root=$HARNESS_ROOT/projects/$PROJECT`, which resolves nowhere for `jarvis`) now calls
  `project_root_path "$PROJECT"`. New scenario appended to `tests/task-teardown.test.sh`: a
  `jarvis`-owned task record with no `project_root` field tears down cleanly.
- **Finding 5 (stale docs).** `docs/herdr-runtime.md` (State section, and the Spawn bullet under
  Behaviour) and `README.md` (nested-onboarding step 3) no longer claim a shared root `plan/` can
  never exist; both now name the reserved `jarvis` exception, matching `RULES.md`'s existing
  wording. No test — documentation only.

Also updated the plan card: appended `## Review round 1` (verdict, findings, fixes) and rewrote
`**Next:**` to dispatch round 2 of 2 against `92dc2ee..HEAD` plus those findings.

## What I rejected, and why

- Did not make `fleet-snapshot.sh` source `herdr-runtime-lib.sh` to pick up the finding-1 guard. It
  computes its own `ROOT` independently and always has; the review named "include root cards" as the
  finding-3 fix, not a resolver change, and `fleet-snapshot.sh` run directly from inside a linked
  worktree is a cwd-relative read exactly like `plan-check.sh`/`checkpoint.sh` — the review said that
  class is correct and should not change. Composed through `session-start.sh` (which does source the
  library and is now guard-corrected), `fleet-snapshot.sh` is invoked by the corrected absolute path
  and inherits the fix without changes to itself.
- Did not choose "die for state-mutating entry points" (finding 1's other offered option) over
  re-resolving. Re-resolving is centralized in the one library every relevant script already sources,
  needs no per-script classification, and keeps read-only scripts like `session-start.sh` honest
  about the real fleet state too — not just the scripts that write to it.

## What changed and why

Round 2 found that the round-1 fix for finding 1 chose silent redirect over refusal — the opposite
of what was asked — and that the redirect's own linked-worktree detection could be fooled by a
submodule. Per the user's decision to enforce the strict boundary, this round adds the refusal
without removing the redirect (read-only inspection still needs it) and hardens the detection.

- `scripts/herdr-runtime-lib.sh`: linked-worktree detection now compares `git rev-parse --git-dir`
  against `--git-common-dir` (they differ only for a genuine linked worktree; a submodule's own
  git-dir and common-dir are the same path) and requires the resolved candidate root to actually
  contain `scripts/herdr-runtime-lib.sh` before trusting it. Sets `IS_JARVIS_LINKED_WORKTREE` and
  `JARVIS_LINKED_WORKTREE_PATH`, and adds `require_fleet_mutation_allowed()`, which dies naming the
  linked worktree and pointing at the canonical checkout when called from one.
- `scripts/harness-state-lib.sh`: `state_lock_acquire()` — the one choke point every fleet-mutating
  entry point already passes through (`agent-spawn.sh`, `agent-review.sh`, `agent-stop.sh`,
  `agent-switch.sh`, `agent-reconcile.sh`, `task-teardown.sh --execute`, `clean-slate-protocol.sh`,
  `events-poll.sh`, `decisions.sh`, `inbox.sh`) — now calls the guard first. No caller needed
  individual changes: the refusal is centralized at the lock primitive, not scattered per script.
- `scripts/herdr-runtime-lib.sh`: `workspace_ensure()` and `atomic_meta_write()` also call the guard
  directly, as defense in depth for any mutation path that does not go through a task-scoped lock
  (e.g. the shared Herdr workspace record).
- `scripts/fleet-snapshot.sh`: now sources `herdr-runtime-lib.sh` and uses its `$HARNESS_ROOT` /
  `$HARNESS_STATE` instead of computing its own `BASH_SOURCE`-derived root, closing the split-brain
  the round-2 report flagged as a non-blocking observation (run directly from inside a linked
  worktree, it previously read a different `.harness-state`/`plan/` than every other script in the
  same session). It stays read-only and is not gated by the new guard.
- `tests/state-lock.test.sh`: rebuilt against an isolated fixture repo instead of sourcing the
  ambient checkout directly. That assumption broke the moment the guard shipped — this very worktree
  is itself a linked Jarvis worktree, so the un-isolated version of this test now legitimately trips
  the new refusal. The fix is not a workaround for the guard: it is what the test should have done
  from the start, and it is now robust to running from any context.
- `tests/root-project-worktree-guard.test.sh`: four new cases — (a) `state_lock_acquire` refuses
  with a message naming the linked worktree and directing to the canonical checkout, and leaves no
  lock behind; (b) sourcing the libs alone (read-only) still succeeds from inside the worktree; (c)
  `fleet-snapshot.sh` run directly from inside the worktree sees a card committed to the canonical
  checkout only, after the worktree was created, proving it no longer split-brains; (d) a real git
  submodule fixture (`git submodule add`) is never mistaken for a linked worktree and `HARNESS_ROOT`
  stays put rather than resolving into `.git/modules`.

Verified each new test fails without its corresponding fix: removing the `require_fleet_mutation_allowed`
call reproduces the round-2 "silently succeeds" hazard; reverting the git-dir/git-common-dir
distinction to the round-1 naive `.git`-is-a-file check reproduces the submodule misfire, both
caught by the new assertions before they were fixed.

## What I deliberately did not do

- Did not add the guard to `plan-check.sh`, `checkpoint.sh`, or `review-rounds.sh` — round 1 already
  established these read the worktree's own `plan/` by cwd, never through the library's `HARNESS_ROOT`,
  and that is correct, unchanged behavior.
- Did not touch `agent-review.sh`, `agent-wait.sh`, or QA verdict routing — out of the original
  card's scope, and the centralized `state_lock_acquire` gate covers `agent-review.sh`'s mutation
  path without editing the file.
