## Finding 1 — the probe prompt contains the marker lines it greps for, so a real preflight can never pass (CONFIRMED)

`scripts/agent-engine-lib.sh:141-147`. The new verdict requires exactly one PASS marker line and
zero FAIL marker lines across the whole captured output. But `capability_preflight_prompt`
(`scripts/agent-engine-lib.sh:130` and `:133`) emits both markers as literal, standalone instruction
lines — measured on the real function, they are lines 12 and 16 of the generated prompt:

```
12:CAPABILITY_PREFLIGHT_RESULT PASS
16:CAPABILITY_PREFLIGHT_RESULT FAIL <capability>
```

`capability_preflight_pass` (`scripts/agent-engine-lib.sh:160`) reads the verdict from
`herdr agent read --source recent-unwrapped --lines 200`, which `herdr agent read --help` documents
as a "Terminal snapshot source" that reads "agent terminal output" — not the agent's reply alone.

I established empirically that this snapshot contains the **delivered prompt verbatim**, using this
reviewer's own live pane (`h_260902_1545_001_claude_1668897`) as the subject. The discriminator:
text that exists only in the appended system prompt versus text that exists only in the delivered
prompt.

| Probe of the live snapshot | Matching lines |
| --- | --- |
| `RULES.md`-only strings (`68% of the lead transcript`, `Round ceiling: two`, `paste into a project`) — system prompt | 0 |
| Card-only strings (`capability-aware-design-qa`, `Engineer checkpoint`, `HOW TO USE THIS FILE`) — delivered prompt | 3 |

`engine_start` puts `RULES.md` in `--append-system-prompt-file` and never in the prompt, so zero
system-prompt matches beside three delivered-prompt matches shows the pane echoes what
`herdr agent prompt` delivers, and `agent read` returns it.

Consequence, reproduced with the real `capability_preflight_prompt` and
`capability_preflight_verdict` on a snapshot built as `echoed prompt + authenticated agent's PASS
reply`:

```
VERDICT: FAIL  <-- authenticated agent judged as failed preflight
```

The echo alone contributes `pass_count=1` and `fail_count=1` before the agent replies at all; the
agent's genuine PASS makes `pass_count=2`. Both conditions in the guard fail. So every role that
declares `capabilities:` in its frontmatter becomes permanently undispatchable through
`agent-spawn.sh`, `agent-review.sh` and `agent-switch.sh`, including the `design-qa` role this task
exists to gate. The preflight read happens immediately after the probe is sent, so the ~16-line
prompt is always inside the 200-line tail window.

This is a regression introduced by this delta, not a pre-existing defect: the round-1 parser took
the last non-blank line and was therefore immune to the echoed instruction text above it.

It is fail-closed, so it is not a security hole — but it disables the feature outright, and it is
the same defect class as the round-1 finding: the parser is being asked to judge a terminal snapshot
that carries far more than the agent's verdict.

Note that the delta's own new assertion at `tests/capability-preflight.test.sh` — duplicate PASS
markers must not pass — is in direct tension with this. The echoed prompt guarantees a second PASS
marker on every real run, so "reject duplicate PASS" and "work in production" cannot both hold while
the prompt shows the marker verbatim.

**Direction (not implemented — this review is read-only).** Take the LAST line matching
`CAPABILITY_PREFLIGHT_RESULT .*` and require it to be exactly `CAPABILITY_PREFLIGHT_RESULT PASS`.
That closes round 1's finding (harmless chatter after the marker no longer breaks it), survives the
echo, and still rejects a missing marker, a malformed marker, a FAIL, and a PASS later contradicted
by a FAIL. The deeper fix is to stop parsing the whole pane — scope the read to the agent's reply, or
stop printing the literal marker inside its own instructions — and either makes the ordering rule
unnecessary.

## Finding 2 — a bare `FAIL` marker is counted as neither pass nor fail, so PASS + FAIL is approved (CONFIRMED, fail-open)

`scripts/agent-engine-lib.sh:145`. The FAIL pattern is `grep -cx 'CAPABILITY_PREFLIGHT_RESULT FAIL .*'`.
Under `-x` the trailing `.*` is preceded by a mandatory space, so the pattern only matches a FAIL
marker that names a capability. A bare `CAPABILITY_PREFLIGHT_RESULT FAIL` line matches neither
counter. Reproduced against the real function:

| Output | Verdict |
| --- | --- |
| `CAPABILITY_PREFLIGHT_RESULT PASS` + `CAPABILITY_PREFLIGHT_RESULT FAIL figma` | fails, correct |
| `CAPABILITY_PREFLIGHT_RESULT PASS` + `CAPABILITY_PREFLIGHT_RESULT FAIL` | **passes** |
| `CAPABILITY_PREFLIGHT_RESULT FAIL` alone | fails, correct |

The bare FAIL alone still fails closed because `pass_count` is 0, which is why the suite misses it.
The contradictory pair is the fail-open case: an agent that answers PASS and then corrects itself
with a FAIL it forgot to name has its substantive brief delivered anyway. Round 1 explicitly
required rejecting contradictory markers, so this is the round-1 finding still open in a narrower
form. Dropping the mandatory space (`FAIL.*`), or counting all `CAPABILITY_PREFLIGHT_RESULT .*`
lines, closes it; the last-marker-wins shape in finding 1 closes it too.
