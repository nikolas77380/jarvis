## Findings

### 1. Running any harness script from a `jarvis` worktree now dispatches against that worktree (medium-high)

`scripts/herdr-runtime-lib.sh:6` derives `HARNESS_ROOT` from the library's own location. A root
project worktree contains the harness's own `scripts/`, so inside it `HARNESS_ROOT` is the worktree.
Before this change that was fail-safe: `plan_card_matches` scanned only `$HARNESS_ROOT/projects`,
which is gitignored (`/projects/`) and therefore absent in every worktree, so `task_card` died with
`found 0`. After this change `$HARNESS_ROOT/plan` exists in the worktree and resolution succeeds
against it.

Measured in this worktree: card, project (`jarvis`), `project_root_path` and `HARNESS_STATE` all
resolve into the worktree. Consequence: `agent-spawn.sh` run by an agent inside a `jarvis` worktree
would create a nested worktree under `<worktree>/.harness-worktrees/jarvis/<id>` and write task
metadata to `<worktree>/.harness-state`, invisible to the real runtime - a forked fleet with no
error. This hazard exists only for the root project, i.e. it is created by this feature (a nested
project's worktree does not contain harness scripts, and invoking them by absolute path resolves
`HARNESS_ROOT` to the harness root correctly).

This needs either a guard or an explicit decision by the lead. Cheapest guard: in
`herdr-runtime-lib.sh`, detect a linked worktree (`.git` is a file, not a directory) and either
re-resolve to the main checkout via `git rev-parse --path-format=absolute --git-common-dir`, or die
for the state-mutating entry points. Note that the cwd-relative scripts (`plan-check.sh`,
`checkpoint.sh`, `review-rounds.sh`) reading the worktree's own `plan/` is correct and should not be
changed.

### 2. `session-start.sh` never discovers the root plan (medium)

`scripts/session-start.sh:34` hardcodes `INDEX="$HARNESS_ROOT/projects/$PROJECT/plan/INDEX.md"` and
`:43` globs `"$HARNESS_ROOT"/projects/*/plan/INDEX.md`. Neither path can reach `$HARNESS_ROOT/plan`.
So `scripts/session-start.sh --project jarvis` prints `(jarvis/plan/INDEX.md not installed)` while
`plan/INDEX.md` exists at the root, and the no-project form omits the harness's own active cards
entirely. The file already sources `herdr-runtime-lib.sh:5`, so the fix is `project_root_path` on
line 34 plus adding the root INDEX to the enumeration on line 43. "Root plan discovery" is a named
scope item on the card, and this is the lead's documented recovery view for the very harness the
feature exists to dogfood.

### 3. `fleet-snapshot.sh` excludes root plan cards (medium)

`scripts/fleet-snapshot.sh:17` walks `"$ROOT"/projects/*/plan/*.md` only. A root card that has no
runtime metadata yet never appears in FLEET STATE (a root card that has been spawned is still picked
up through the `.harness-state/*.meta` walk, so the gap is card-without-metadata: freshly minted, or
torn down). Measured above: zero rows with a root card present. Same one-line class of fix as
finding 2.

### 4. `task-teardown.sh` fallback bypasses the resolver (low)

`scripts/task-teardown.sh:24` still falls back to `"$HARNESS_ROOT/projects/$PROJECT"` when metadata
carries no `project_root`. For `jarvis` that resolves to a non-existent path and the script dies at
`:30` with `project root is unavailable` rather than resolving the root. It fails safe and only
legacy metadata reaches it, so this is not a blocker - but it is the exact inline drift that
`project_root_path`'s own comment forbids, and it is one substitution.

### 5. Documentation now contradicts the code (low)

`docs/herdr-runtime.md:36-37` ("never in a shared `plan/` at the harness root"), `:56` ("scanning
`projects/*/plan/`") and `README.md:74` state the invariant this PR deliberately changed. The card
scope asked for stale text that says root plans can never exist to be updated; `RULES.md` and the
two template copies were updated, these three were not. A future agent reading `docs/herdr-runtime.md`
re-derives the wrong invariant, which is the failure this PR is otherwise fixing.
