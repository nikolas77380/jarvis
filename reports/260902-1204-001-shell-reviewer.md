## Findings

### 1. BLOCKING - the fresh-macOS path aborts after a successful installer run

`bootstrap.sh:60-78` (`ensure_herdr`, `ensure_claude`) confirm the install with `command -v` against
the *current process* PATH. `ensure_path_export` (`bootstrap.sh:80-88`, called at line 155) only
appends to `~/.zprofile`; it never adds `$HOME/.local/bin` to the running shell's PATH, and it runs
*after* both installers anyway.

Both official installers put their binary in `~/.local/bin`. Measured on this host:

```
$ command -v claude   -> /Users/nikolaykipniak/.local/bin/claude
$ command -v herdr    -> /Users/nikolaykipniak/.local/bin/herdr
```

That is the very directory `verify` (`bootstrap.sh:137-142`) already assumes may be absent from PATH.
So on a genuinely fresh macOS, where `~/.local/bin` is not on PATH yet, the installer succeeds and
bootstrap then declares it failed.

Reproduced with a fixture whose fake installers write into `$HOME/.local/bin` (as the real ones do)
while PATH excludes it:

```
installing herdr: curl -fsSL https://herdr.dev/install.sh | sh
error: herdr installation did not put herdr on PATH
--- what the installer actually produced ---
-rwxr-xr-x  1 ... $HOME/.local/bin/herdr
```

`ensure_claude` fails identically once `herdr` is out of the way. This is the primary scenario the
script exists for, and it fails closed with a misleading message.

Why the suite misses it: `fake_curl` writes its executables into `$BOOTSTRAP_TEST_BIN`
(`tests/bootstrap.test.sh:88` and `:95`), and `run_bootstrap` sets `PATH="$dir/bin"` to that same
directory (`tests/bootstrap.test.sh:113`). The fixture installer therefore always installs onto PATH,
which no real installer guarantees. The test proves the fake, not the behaviour.

Fix: add `export PATH="$HOME/.local/bin:$PATH"` (idempotently) inside `bootstrap.sh` before the
installer steps, so the process can see what the installers wrote. Add a case whose fake installer
targets `$HOME/.local/bin` while PATH excludes it.

### 2. BLOCKING - `mv` onto a directory destination moves the link inside it instead of replacing it

`bootstrap.sh:119-121`:

```sh
tmp_link="$local_bin/.jarvis.bootstrap.$$"
ln -s "$JARVIS_BIN" "$tmp_link"
mv "$tmp_link" "$JARVIS_LINK"
```

BSD `mv` resolves a directory destination (and follows a symlink to one) and moves the source
*into* it. Measured on this macOS:

```
$ ln -s /etc/hosts tmp_link && mv tmp_link dest_dir
$ ls dest_dir      -> tmp_link -> /etc/hosts          # dest_dir intact, link moved inside

$ ln -s "$PWD/realdir" jarvis && ln -s /etc/hosts tmp2 && mv tmp2 jarvis
$ ls -la .         -> jarvis -> .../realdir           # unchanged
$ ls -la realdir   -> tmp2 -> /etc/hosts              # link landed inside the target
```

Two reachable paths:

- `bootstrap.sh:116-118` - the destination is a **directory**. `confirm_replace` asks, the user
  says yes, and nothing is replaced: `~/.local/bin/jarvis` stays a directory with a stray
  `.jarvis.bootstrap.<pid>` symlink inside it. `verify` then dies at `bootstrap.sh:133`
  ("is not a symlink") after the mutation, so a granted confirmation produces both a failure and
  litter.
- `bootstrap.sh:109-115` - a stale symlink pointing at a **directory**. This branch does not prompt
  at all ("a stale symlink is always safe to repair"), so the repair silently does nothing and drops
  a stray symlink inside whatever directory the old link pointed to.

Neither case is covered: test 8 uses a symlink to a non-existent file
(`tests/bootstrap.test.sh:263`), and test 9 plus both interactive cases use a regular file.

Fix: unlink the destination explicitly before the atomic rename (BSD `mv` has no `-T`), or use
`ln -sfn`, and extend `ensure_symlink`'s handling to reject a directory destination outright rather
than routing it through `confirm_replace` as if replacement would work. Add both directory cases to
the suite.

### 3. NON-BLOCKING - `ZDOTDIR` is ignored, so the PATH export can land in an unread file

`bootstrap.sh:81` uses `$HOME/.zprofile` unconditionally. When `ZDOTDIR` is set, zsh reads
`$ZDOTDIR/.zprofile` and never looks at `$HOME/.zprofile`, so the export is written to a file that
is never sourced and `jarvis` silently never reaches PATH, while bootstrap reports success and
`verify` prints the reassuring "added to ~/.zprofile" line.

The repo already has the convention: `bin/jarvis install-alias` uses `${ZDOTDIR:-$HOME}/.zshrc`
(`bin/jarvis:108`). Use `${ZDOTDIR:-$HOME}/.zprofile` for consistency, and reflect the resolved path
in the messages at `bootstrap.sh:83`, `:87`, and `:141`.

### 4. MINOR - `~/.zprofile` is mutated before the symlink step can refuse

`main` runs `ensure_path_export` (line 155) before `ensure_symlink` (line 156). When the destination
is unexpected and confirmation is refused (`bootstrap.sh:117`), the run fails with `~/.zprofile`
already edited. Test 9 asserts the destination file was not mutated
(`tests/bootstrap.test.sh:287-288`) but says nothing about the profile, so the behaviour is
unspecified rather than chosen. Either move `ensure_path_export` after `ensure_symlink` - which also
matches the card's own staging intent - or assert the current behaviour deliberately.

### 5. MINOR - the temp symlink leaks when `mv` fails

`bootstrap.sh:119-121` has no trap or cleanup, so any `mv` failure leaves
`~/.local/bin/.jarvis.bootstrap.<pid>` behind under `set -e`. A `trap`-based cleanup, or `rm -f` on
the failure path, keeps a failed run from accumulating files in a directory that is about to be put
on the user's PATH.

### 6. MINOR - the symlink-resolution loop has no iteration cap

`bootstrap.sh:9-16` and `bin/jarvis:4-11` loop `while [ -h "$SOURCE" ]` with no bound, so a symlink
cycle spins forever rather than failing. `bin/jarvis` is the shared entry point every command goes
through, which makes the cheap guard (a counter capped at roughly 40, then `die`) worth having.

## What is good

- The root-resolution fix in `bin/jarvis:3-12` is the correct idiom, is genuinely required by the
  symlink this task installs, is recorded on the card with the user's approval, and is actually
  exercised end to end: `verify` invokes `"$JARVIS_LINK" status` (`bootstrap.sh:143`), so the fresh
  and path-with-spaces cases run `bin/jarvis` *through* the installed symlink. Removing the loop
  would turn those cases red.
- The fixture isolation is real: per-case HOME, a curated PATH directory, its own copy of the clone
  plus the three libs `bin/jarvis` sources, and `never_call` shims that make an unexpected `brew` or
  `curl` invocation a test failure. Nothing reaches the real machine.
- `TMP="$(cd "$(mktemp -d)" && pwd -P)"` with the comment explaining the
  `/var` vs `/private/var` mismatch is exactly the kind of trap that normally costs a debugging
  session.
- The interactive `pty` driver covers the one branch a pipe cannot fake, in both directions.
- Idempotence is properly asserted rather than claimed: case 2 fails if `brew` or `curl` is invoked
  at all, and case 7 runs bootstrap twice and counts the profile line.
- Homebrew is printed and never executed, and case 3 asserts no `.zprofile` and no symlink were
  created on that path.
- `docs/herdr-runtime.md` explains *why* the resolution loop exists rather than only that it does.
