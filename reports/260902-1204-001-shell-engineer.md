## What changed and why

Added `bootstrap.sh`, a one-command macOS onboarding script for a fresh clone, built with TDD
against fixture-isolated HOME/PATH throughout (no test ever touches the real machine).

- `bootstrap.sh`: requires Darwin (fails clearly otherwise); requires `brew` (prints the official
  install command/URL and stops without executing it if missing); installs `git`/`jq` with Homebrew
  only when missing, never upgrading; installs `herdr`
  (`curl -fsSL https://herdr.dev/install.sh | sh`) and Claude Code
  (`curl -fsSL https://claude.ai/install.sh | bash -s stable`) only when missing; links
  `~/.local/bin/jarvis` to this clone's absolute `bin/jarvis` and adds `~/.local/bin` to `PATH` via
  `~/.zprofile` (deduplicated); repairs a stale symlink silently but asks before replacing an
  unexpected file, refusing without any mutation when not running under a terminal; runs all
  dependency installs before the symlink publish step so a failed install can never leave a broken
  `jarvis` command; verifies every tool, the symlink target, PATH, and a read-only
  `bin/jarvis status`; and prints exactly two next actions (`Authenticate: claude`,
  `Start Jarvis: jarvis claude`). All paths are quoted throughout, including clone paths containing
  spaces.
- `bin/jarvis`: fixed root-directory resolution to follow symlinks (a loop, matching the standard
  idiom) instead of a plain `dirname "${BASH_SOURCE[0]}"`. **Found during implementation, confirmed
  with the user before proceeding** (out of this card's original `Owns:`): bash does not resolve
  symlinks in `BASH_SOURCE`, so the literal `~/.local/bin/jarvis` symlink this task creates would,
  once invoked via `PATH`, compute the wrong root and fail to source `scripts/` — this is why the
  pre-existing `bin/jarvis install-alias` command uses a shell alias with a baked-in path instead of
  a symlink. The user chose "fix `bin/jarvis`" over the other two options offered (stop and report;
  or ship the literal symlink and accept the breakage). This is the only change to `bin/jarvis`;
  `tests/jarvis-cli.test.sh` (unchanged, still green) plus this task's own symlink-invocation
  coverage in `tests/bootstrap.test.sh`/`tests/bootstrap-interactive.test.sh` (which run
  `bin/jarvis status` **through** the installed symlink, not the raw path) are what caught it and
  what now guard it. Recorded on the card under "Discovered during implementation".
- `tests/bootstrap.test.sh`: fresh install, fully installed rerun (brew/curl log empty — never
  invoked), missing Homebrew, non-macOS, dependency install failure (staging proof: neither the
  symlink nor `~/.zprofile` exist afterward), path with spaces (clone lives under `"My Clone"`),
  profile deduplication (two consecutive runs, one export line, unrelated content preserved),
  expected symlink repair (stale target, no prompt, non-interactive), unexpected destination
  refusal (regular file, non-interactive, byte-for-byte unchanged after refusal). Each case gets its
  own fully isolated fixture: its own `HOME`, its own curated bin dir standing in for `PATH` (real
  host git/jq/herdr/claude/brew/curl/uname are never reachable — only what a case stages), and its
  own copy of the clone.
- `tests/bootstrap-interactive.test.sh`: the one path that needs a real terminal
  (`[ -t 0 ]`/`[ -t 1 ]` can't be faked with a pipe) — drives `bootstrap.sh` under an actual
  pseudo-terminal via Python's `pty` module (already a project dependency; see
  `scripts/agent-spend.sh`/`scripts/context-size.sh`) and feeds the reply through it. Covers both
  accepting and declining the replacement of an unexpected destination.
- `README.md`: rewrote Initial-setup step 1 to describe `bootstrap.sh` end-to-end with the exact
  installer commands and URLs; the Herdr-runtime section now points at `bootstrap.sh` as the normal
  path and reframes `bin/jarvis install-alias` as the older manual alternative.
- `docs/herdr-runtime.md`: added a `## bootstrap.sh` section (behavior, staging, verification) and
  the command to the command list; documented the symlink-resolution fix and why it was needed.

## What I rejected, and why

- Did not make `bootstrap.sh` verify by invoking `bin/jarvis status` at its raw clone path. The
  brief's checklist separately names "the symlink target" and "read-only `bin/jarvis status`" as
  distinct verification items; invoking `status` through the installed `~/.local/bin/jarvis` symlink
  instead proves the actual thing a user will run works end-to-end, and is exactly what caught the
  root-resolution bug above during design — verifying the raw path would have hidden it.
- Did not add a shared `tests/` helper library for the two bootstrap test files. No other file in
  `tests/` sources a shared fixture library; each is self-contained. The ~30-line fixture-builder is
  duplicated between the two files rather than introducing a new convention outside this card's
  `Owns:`.
- Did not use `readlink -f` for symlink resolution in `bin/jarvis`/`bootstrap.sh` even though it
  works on this machine's BSD `readlink`. The manual loop is the older, more portable idiom (works
  on any bash 3.2+/BSD `readlink` without `-f` support) and needed no new external dependency.
- Did not touch `bin/jarvis install-alias` itself. It remains a valid, working alternative path; the
  README now explains the relationship instead of removing or changing it.

## Findings 1-3 (blockers): closed, each with a regression test proven to fail pre-fix

Every regression test below was run against the pre-fix `bootstrap.sh`/`bin/jarvis` (checked out
from the round-1 tip) to confirm it actually fails there, then against the fix to confirm it passes
— not just added and left green.

1. **PATH excluded `$HOME/.local/bin` while installers ran.** Added
   `ensure_local_bin_on_path`/`local_bin_already_on_path` (`bootstrap.sh:67-78`), called in `main`
   right after `require_brew`, before any installer step. This only exports onto the running
   process's `PATH`; it does not touch any profile file. Regression: `tests/bootstrap.test.sh` case
   10, with a new `fake_curl_to_home` fixture that writes the fake `herdr`/`claude` binaries into
   `$HOME/.local/bin` (matching what the real installers do) while `PATH` excludes it — fails on the
   pre-fix script with `herdr installation did not put herdr on PATH`, passes on the fix.
2. **`mv` onto a directory destination.** `ensure_symlink` (`bootstrap.sh:119-143`) now (a) rejects a
   real directory at the destination outright with `die`, before ever asking for confirmation — a
   directory can never be safely replaced by `mv`, so routing it through `confirm_replace` as if
   replacement would work was itself wrong, not just the `mv`; and (b) replaces the destination with
   an explicit `rm -f "$JARVIS_LINK"` before the `mv`, since a symlink pointing at a directory is
   followed by `mv` the same way a real directory is. Two regressions, both proven to fail pre-fix:
   `tests/bootstrap.test.sh` case 12 (stale symlink pointing at a directory — pre-fix left a
   `.jarvis.bootstrap.<pid>` file inside the old target directory instead of repairing the link) and
   `tests/bootstrap-interactive.test.sh` case 3 (a real directory at the destination, user replies
   "y" over a pty — pre-fix accepted the confirmation, then left litter inside the directory and
   never replaced it). The non-interactive directory case (`tests/bootstrap.test.sh` case 11) passes
   on both old and new code because non-interactive `confirm_replace` already refused before `mv`
   ever ran; it stays as coverage that non-interactive directory refusal doesn't regress, and the
   interactive case is what actually reproduces the reviewer's finding.
3. **`ZDOTDIR` ignored.** Introduced `ZPROFILE="${ZDOTDIR:-$HOME}/.zprofile"` at the top of
   `bootstrap.sh` (matching the existing `bin/jarvis install-alias` convention at `bin/jarvis:108`)
   and used it everywhere the script previously hardcoded `$HOME/.zprofile`
   (`ensure_path_export`, the `verify` PATH message). Regression: `tests/bootstrap.test.sh` case 13,
   run with `ZDOTDIR` set to a directory distinct from `$HOME` — fails pre-fix (export lands in
   `$HOME/.zprofile` instead), passes on the fix.

## Findings 4-6 (engineer's call): all three fixed

4. **Profile mutated before a symlink refusal.** Reordered `main` so `ensure_symlink` runs before
   `ensure_path_export` (`bootstrap.sh:166-179`) — a refusal now happens before the profile is ever
   touched. Regression: added an assertion to `tests/bootstrap.test.sh` case 9 that `~/.zprofile`
   does not exist after the unexpected-destination refusal; fails pre-fix, passes on the fix. Fixed
   rather than declined: this is the same function ordering finding 1 already required touching, and
   leaving the write-before-refuse behavior unspecified sits against the brief's own "stage risky
   writes" requirement (item 5).
5. **Temp symlink leak on `mv` failure.** Wrapped the stage-then-swap in `ensure_symlink` with a
   narrow `trap 'rm -f "$tmp_link"' EXIT`, cleared with `trap - EXIT` right after a successful `mv`
   (`bootstrap.sh:134-141`). `bootstrap.sh` installs no other trap, so this doesn't collide with
   anything. Fixed rather than declined: cheap, and the trap fires whether `set -e` aborts the script
   or `mv` fails.
6. **Unbounded symlink-resolution loop.** Added a 40-hop cap to the resolution loop in both
   `bootstrap.sh:8-22` and `bin/jarvis:3-16`, failing with a clear message instead of spinning
   forever on a cycle. Fixed rather than declined per the reviewer's own note that `bin/jarvis` is the
   shared entry point every command goes through.

## Finding 1 (blocking): closed, reproduced pre-fix first

The round-2 report's exact reproduction was run before touching anything: `ZDOTDIR=<sentinel>
bash tests/bootstrap.test.sh` went red at case 1 (`PATH export missing from ~/.zprofile`) and left a
real `.zprofile` inside the sentinel directory; `ZDOTDIR=<sentinel2>
bash tests/bootstrap-interactive.test.sh` passed 3/3 while silently writing into the sentinel. Both
confirmed exactly as the reviewer described.

Root cause was one layer deeper than the reviewer's suggested one-line fix: pinning
`ZDOTDIR="${ZDOTDIR:-$dir/home}"` alone doesn't help when the *invoking* shell already has `ZDOTDIR`
exported (the common case the finding itself is about) — the `:-` default never triggers, because
`$ZDOTDIR` is non-empty at the point the function reads it. Verified this with a standalone repro
(`ZDOTDIR=custom f`, where `f` used `${ZDOTDIR:-default}` — printed `custom`, not the default).

Fix, two parts:
- `unset ZDOTDIR` added right after `set -euo pipefail` in both `tests/bootstrap.test.sh` and
  `tests/bootstrap-interactive.test.sh`, so the suite's own claimed isolation ("Nothing here ever
  touches the real machine") no longer depends on what the invoking shell happens to export.
- `ZDOTDIR="${ZDOTDIR:-$dir/home}"` added to the env prefix in `run_bootstrap`
  (`tests/bootstrap.test.sh:139`) and `run_bootstrap_pty`
  (`tests/bootstrap-interactive.test.sh:83`), so each case gets its own fixture `$dir/home` by
  default.
- Case 13 now overrides per-invocation instead of exporting into the whole suite:
  `ZDOTDIR="$D/home/customzdotdir" run_bootstrap "$D"` (`tests/bootstrap.test.sh:393`), confirmed
  this still reaches the function body (a bash `VAR=val func` prefix is visible inside the function,
  not just in a forked process — verified standalone before relying on it).

Re-ran both sentinel reproductions after the fix: `tests/bootstrap.test.sh` 13/13 green with the
sentinel untouched (empty directory); `tests/bootstrap-interactive.test.sh` 3/3 green with its
sentinel untouched. Full suite re-run clean, 21/21.

## Finding 2 (minor): doc reworded to the measured behavior

`docs/herdr-runtime.md`'s symlink-cycle sentence no longer claims the 40-hop cap "turns a symlink
cycle into a clear failure instead of a hang" — per the round-2 measurement, a cycle in the
invocation path never hangs either way; the OS already refuses it at `exec` with "Too many levels of
symbolic links" before bash reads the script. Reworded to say the cap bounds the script's own
resolution loop and is a cheap guard on that loop, not what protects against a cyclic invocation
path. No code change, as the report noted.
