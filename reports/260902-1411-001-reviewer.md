## Blockers

### 1. `tools:` frontmatter is inert - the read-only researcher authority is prose only, and the new test asserts it as if it were enforced

`agents/deps-researcher.md:4` declares `tools: Read, Grep, Glob, Bash, WebSearch, WebFetch`, and
`tests/role-resolution.test.sh:135-139` asserts that line excludes `Edit`/`Write`. Nothing consumes
the field. `engine_start()` in `scripts/agent-engine-lib.sh` reads exactly `claude_model`/`model`,
`claude_effort`/`effort`, `codex_model` and (separately) `capabilities`; line 210 launches the
session as:

    args=(--append-system-prompt-file "$system" --name "$task" --permission-mode bypassPermissions)

No `--allowedTools`, no `--disallowedTools`, no tool restriction of any kind, and
`bypassPermissions` on top.

Failure scenario: the lead dispatches `deps-researcher` on "replace the unmaintained date library".
The session comes up with the full tool set under bypassPermissions. Nothing prevents it from
editing `package.json`, running `npm install`, or writing a lockfile - the very actions the role's
"Hard limits" (`deps-researcher.md:118-120`) forbid. The run returns a recommendation, the lead
reads "read-only" in `RULES.md:33-37` and in the PR body, and trusts that no files changed. On a
project whose engineer is concurrently holding that same `package.json`, that is a silent
cross-agent write.

The user's explicit choice in the grill-me interview was read-only researcher authority. What
shipped is a role that *says* read-only, plus a test that certifies a field with no runtime effect.
That combination is worse than no field at all: it converts an unenforced property into a
mechanically "verified" one.

Second half of the same problem: even if `tools:` were honored, `Bash` is granted (line 4), and
`Bash` alone can install packages and write files. `nestjs-reviewer.md:4` and
`nextjs-reviewer.md:4` declare `tools: Read, Grep, Glob, Bash` and call themselves "Read-only" in
their descriptions - same gap.

What I would accept:
- Drop the `tools:` lines, or implement them in `engine_start()` (a `role_field "$role" tools` ->
  `--allowedTools` pass-through for the claude engine, with the codex equivalent), and change the
  test to assert the enforced behavior rather than the text of a field. Either direction is fine;
  shipping the field plus the test without the enforcement is not.
- If the field stays declarative, the test comment at `tests/role-resolution.test.sh:133-134`
  ("deps-researcher is read-only: its declared tools must exclude Edit/Write") must say it checks a
  declaration, not a restriction.

right instrument at `:84-88` - read the migration and reason about rolling-deploy safety.

### 5. Both engineer roles instruct a dispatch the engineer cannot perform

subagent to play researcher (violating `RULES.md:59-61`, "Do not dispatch implementation or review

already at `nestjs-engineer.md:24-26` / `nextjs-engineer.md:27-28`.

### 6. The highest-blast-radius Next.js constraint is keyed on a filename current Next.js no longer uses

`nextjs-engineer.md:62-63` ("Never add or change `middleware.ts`. Middleware runs on every matched
request; a mistake there takes down or exposes the whole app at once") and `nextjs-reviewer.md:77`
("Add or modify `middleware.ts` - it runs on every matched request", inside the
constraint-compliance list whose violations are blockers reported first).

Next.js 16 renamed `middleware.ts` to `proxy.ts` (exported function `middleware` -> `proxy`,
codemod `npx @next/codemod@canary middleware-to-proxy .`); `middleware.ts` is deprecated and slated
for removal. On any Next 16+ project the request-level interceptor is `proxy.ts`.

Failure scenario: the engineer adds `proxy.ts` to a Next 16 app. The approval constraint does not
match the filename, so no approval is sought; the reviewer's first-priority constraint check does
not match it either, so it is not a blocker. A file that runs on every matched request lands
unapproved and unflagged - and both roles' own "Never assume the stack" / "never assume framework
facts from this file" instructions were supposed to prevent exactly this kind of baked-in framework
fact.

Fix: key the constraint on the behavior, naming both files - "any request-level interceptor
(`middleware.ts`, or `proxy.ts` on Next 16+ - whatever this project's version calls it)".

Fix: "Lint - the project's lint script, or `eslint`/`biome` directly (`next lint` was removed in
Next 16 and `next build` no longer lints)".

`.claude/stack.yml`, or wherever this project's `CLAUDE.md` points)". The report
(`reports/260902-1411-001-deputy.md:23-24`) says it "Dropped the Yavo-specific `.claude/stack.yml`

harness has that file. The card's done-criterion is "No global role contains Yavo-specific
repository, path, database, or domain assumptions"; the test's Yavo detector
(`tests/role-resolution.test.sh:126-129`) is name-based, so it cannot see a path that does not
contain the string "yavo".

Small concrete cost: on a project with no such file, the researcher opens its report with "pins
were inferred, not declared" (`:33-34`) - correct. On a project that keeps a policy under a
different name and does point at it from `CLAUDE.md`, the wording is fine. The residue is one word:
"commonly". Suggest "wherever this project's `CLAUDE.md` points (some projects keep one at
`.claude/stack.yml`)", and drop the "Dropped ... requirement" wording from the report, which
overstates what changed.

### 10. `deps-researcher`'s output contract has no durable home

`RULES.md:190-191` has specialists write the long account to `reports/` and return <=15 lines.
`deps-researcher.md:94-114` specifies an under-400-word inline block (verdict, comparison table,
install command, risks, rejected) and no report file - consistent with a role that cannot write, but
it means the evidence behind an adoption decision exists only in a transcript, while
`nestjs-engineer.md:302-304` requires that recommendation to be "on record" for the reviewer to
check. Nothing says where the record lives.

Cheapest fix that keeps the role read-only: one line in `RULES.md`/`orchestrator.md` saying the lead
pastes the researcher's verdict block into the task card (or `docs/decisions/`) before dispatching
the install, so "on record" resolves to a path a reviewer can open.
