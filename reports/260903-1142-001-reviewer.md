# Review round 1 of 2 — PR #6 (tip 96b3054)

**Verdict: REQUEST_CHANGES.** The mechanics the brief asked for are implemented correctly and are
well tested — ack-gating, exact-tab targeting, generation guard, idempotence, retryable close
failure, blocked refusal all hold under test. The problem is one level up: the trigger this design
hangs cleanup on fires for the tab that the existing handoff scripts already close, and never fires
for the tab that actually accumulates — and running the command at the moment `agents/orchestrator.md`
now instructs makes the task unreviewable.

## Findings, most severe first

### 1. Following the new orchestrator rule bricks the engineer -> reviewer handoff (blocker)

`agent-cleanup.sh:67` ends in `close_recorded_tab` (`scripts/herdr-runtime-lib.sh:267`), which writes
`stopped=1`. `scripts/agent-review.sh:40` and `scripts/agent-switch.sh:24` both refuse outright on
`stopped=1` (`task agent is stopped; use a relaunch flow`), and `agent-spawn.sh` refuses a second
worktree for the same task id. `agents/orchestrator.md:99-105` tells the lead to run
`scripts/agent-cleanup.sh <event-id>` right after `inbox.sh acknowledge` on an engineer's
`agent-done` event — which is exactly the moment RULES.md requires `agent-review.sh` to hand the same
task, same worktree, to a reviewer.

Failure scenario, reproduced end to end against these scripts with a fake `herdr` (same fixture shape
as `tests/agent-cleanup.test.sh`):

```
step 1: lead acknowledges the engineer's agent-done event
step 2: lead follows agents/orchestrator.md and runs agent-cleanup.sh
cleaned up: t1 · closed settled tab tab1 (generation 1)
step 3: lead follows RULES.md and hands the task to the reviewer
error: task agent is stopped; use a relaunch flow
agent-review.sh exit: 1
```

The task now has no documented path to review: handoff and switch refuse, spawn refuses.

### 2. The tab that actually accumulates can never be cleaned up (blocker)

`scripts/agent-review.sh:92` and `scripts/agent-switch.sh:92` already close the previous tab as the
last step of a handoff. So generation 1's tab is not the one that piles up — the surviving tab is the
last generation's, normally the reviewer's. That tab's `agent-done` event is deduplicated out of
existence: `event_id` keys on `task + type + generation` (`scripts/harness-event-lib.sh:7-9`) where
`events-poll.sh:45` passes the string `"done-$HEAD"`. A reviewer commits nothing, so HEAD is
unchanged from the engineer's done event and the ids collide.

Reproduced with the same fixture — generation 2 (new tab, new agent name, unchanged head) reaching
`done`:

```
-- unread inbox after gen2 finished:
(empty)
-- events file:
{"id":"e_60c1f8691ee58e67","type":"agent-done","generation":"done-h1",
 "identity":{"tab":"tab1","generation":1}}
-- t1 meta after gen2 done:
generation=2
tab=tab2
stopped=0
```

There is no event id for generation 2, so no argument exists to pass to `agent-cleanup.sh`, and
`tab2` stays open permanently. The new `identity` field records a numeric generation that the
deduplication key does not contain — the identity frozen into the event is strictly finer-grained
than the key it is stored under. A second consequence, pre-existing but made load-bearing by this
design: the lead is never notified that the reviewer finished at all.

Fix direction (lead's call, not mine to impose): include the meta generation in the done event's
dedup key, e.g. `event_emit "$TASK" agent-done "$RUNTIME-$HEAD-g$DONE_GENERATION" ...`, so each
execution generation gets its own event and its own frozen identity. That also restores the missing
"reviewer finished" notification. Whatever is chosen needs a test for two generations settling at an
unchanged HEAD.

### 3. "Closed automatically" is documented but not implemented (medium)

`docs/herdr-runtime.md:85` states "Settled tabs are closed automatically", and the card's stated goal
is that completed tabs stop requiring manual cleanup. Nothing in the repo invokes
`scripts/agent-cleanup.sh` — I grepped every `.sh` and `.md`; the only callers are the test and the
prose telling a human to type it. It is a manual command gated on a manual acknowledgement. Related
inaccuracy: `agents/orchestrator.md:101` calls it "the only auto-close path", but
`agent-review.sh:92` and `agent-switch.sh:92` close tabs too. Either wire the close into
`inbox.sh acknowledge` (which is what "automatic" would mean) or reword both claims.

### 4. The frozen identity is assembled from six unlocked reads (low)

`scripts/events-poll.sh:35-45` reads `$HARNESS_STATE/$TASK.meta` without holding that task's state
lock, once per field (`schema`, `generation`, `agent_name`, `tab`, `session`). A concurrent
`agent-review.sh` — which does hold the lock and rewrites the meta atomically — landing between two
of those reads yields a chimeric identity mixing generation 1's agent name with generation 2's tab.
It fails safe (the cleanup guard can never match a chimera, so cleanup no-ops), but the comment at
`events-poll.sh:30-32`, "while the meta file still describes this generation", is a claim nothing
enforces. Worth either taking the task lock around the read or softening the comment.

### 5. The PR's own test-count claim is wrong, and was measured on a stale base (low)

The PR body says the full suite is "21 files". This branch has 20 (`ls tests/*.test.sh | wc -l` -> 20).
`origin/main` has 24; the merged tree has 25. The branch is cut before `b7f3706` (PR #5), so the
engineer's green run never exercised PR #5's five test files or its 107-line `agent-engine-lib.sh`
change. I re-ran the suite on the merged tree: 25/25 pass, so nothing is actually broken — but the
number as written is arithmetic, not a measurement.

### 6. Merge hazard: the PR does not merge cleanly into origin/main (not a code defect)

Trial merge of `96b3054` into `b7f3706` conflicts in four files: `OVERVIEW.md`,
`agents/orchestrator.md`, `plan/INDEX.md`, `plan/260902-1545-001-capability-aware-design-qa.md`.
`scripts/` and `tests/` merge automatically with no conflict. Resolving `agents/orchestrator.md`
toward this branch silently deletes PR #5's anti-proxy invariant; `tests/anti-proxy-rule.test.sh`
catches that (I reproduced both the failure and, after a correct union resolution, the pass).

Also noted, not a defect: the PR carries eight unrelated plan/report/`tasks/` files from earlier lead
commits sitting on this branch. Only `1f0748b` touches `scripts/` or `tests/`. One PR, one concern
would have made this diff a third of its size.
